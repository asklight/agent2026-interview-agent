# 生产入口迁移至 9999 端口设计

日期：2026-08-08

## 背景

当前生产编排通过 `${WEB_PORT:-80}:80` 将 Web 容器发布到宿主机，服务器现有 `.env.prod` 又配置了 `WEB_PORT=80`。公网 `80` 端口并非本项目的可靠独占入口，实际访问返回 `502 Bad Gateway`。

本次变更将项目的生产入口迁移到宿主机 `9999` 端口。容器内部端口保持不变：Web 继续监听 `80`，Server 继续仅在 Docker 网络内监听 `8080`。

## 目标

- 生产页面使用 `http://82.157.209.181:9999/` 访问。
- API 继续由 Web 容器按同源路径 `/api/**` 代理，无需单独暴露后端端口。
- 自动部署能够迁移服务器已有的 `.env.prod`，而不是只改变新环境的默认值。
- 示例配置、运维文档和线上健康检查地址保持一致。
- 不修改数据库、业务接口、JWT 签名密钥及用户数据。

## 方案

### 配置

Compose 保留 `WEB_PORT` 环境变量，以便未来在不同服务器上调整端口，但默认值由 `80` 改为 `9999`。生产环境示例使用：

```dotenv
WEB_PORT=9999
WEB_ORIGIN=http://82.157.209.181:9999
```

### 生产环境迁移

部署脚本在校验配置前，将 `.env.prod` 中的 `WEB_PORT` 设置为 `9999`，并将当前生产地址对应的 `WEB_ORIGIN` 设置为 `http://82.157.209.181:9999`。更新操作必须满足：

- 变量存在时原位替换，只保留一条有效配置。
- 变量不存在时追加。
- 不输出或改写其他敏感变量。
- 重复执行结果一致。

部署随后执行现有的数据库备份、Compose 配置校验、镜像构建、容器健康等待和状态输出流程。Compose 重建 Web 容器时会释放原来的宿主机 `80` 绑定并建立 `9999:80` 映射。

## 请求路径

```text
浏览器 http://82.157.209.181:9999/
  -> 宿主机 TCP 9999
  -> Web 容器 TCP 80
  -> 静态前端

浏览器 http://82.157.209.181:9999/api/**
  -> 宿主机 TCP 9999
  -> Web 容器 Nginx
  -> Server 容器 TCP 8080
```

MySQL 继续只在 Docker 网络中提供 `3306`，不发布到公网。

## 失败处理

- 若宿主机 `9999` 已被占用，Compose 启动失败，自动部署失败并保留明确日志，不回退到 `80`。
- 若 Server 或 Web 健康检查失败，部署脚本以非零状态退出并输出 Compose 状态。
- 部署成功后若公网无法访问，优先检查云安全组和主机防火墙是否放行 TCP `9999`。
- 旧的 `http://82.157.209.181/` 不再作为本项目入口，也不要求本次变更接管或修复该端口上的既有服务。

## 验证

本地和 CI 验证：

- `docker compose -f docker-compose.prod.yml --env-file deploy/env.prod.example config` 显示 Web 发布端口为 `9999`。
- 部署脚本语法检查通过。
- 自动化测试和前端构建不因部署端口调整而失败。

生产验证：

- GitHub Actions 部署任务成功。
- `http://82.157.209.181:9999/` 返回前端页面。
- `http://82.157.209.181:9999/api/health` 返回健康结果。
- `http://82.157.209.181:9999/api/health/db` 返回数据库健康结果。

## 非目标

- 本次不配置域名、HTTPS 或宿主机反向代理。
- 本次不将 Server 的 `8080` 或 MySQL 的 `3306` 暴露到公网。
- 本次不处理 Milvus、知识库或面试业务功能。
